# WireGuard 接收端（服务端）数据包处理与转发流程解析

本文详细解析 WireGuard（特别是以 `wireguard-go` 为代表的用户态实现）在作为 VPN 服务端时，接收数据包、解密校验以及通过系统内核进行 NAT 转发的全过程。

同时，针对容易产生误解的 **“用户态程序是否会过滤非本机网段流量”** 以及 **“数据包如何递交给操作系统”** 进行深入剖析。

---

## 一、 常见误区与正确机制对比

### ❌ 常见误区
> **误区观念**：当 `wireguard-go` 收到外层 UDP 包并解密后，如果发现解密出来的目标 IP（如公网 IP `8.8.8.8`）与服务端本地 TUN 网卡的 IP/网段不一致，`wireguard-go` 用户态程序**不会**把数据包写入 TUN 设备（`tun_fd`），而是直接在后台绕过 TUN 设备交给系统进行转发。

### ✅ 正确机制
> **底层事实**：`wireguard-go` **无论如何都会把解密成功且校验通过的数据包写入 TUN 设备的 `fd`**。
> 
> WireGuard 的定位仅仅是一张**虚拟三层网卡（L3 Network Interface）**，它的职责非常单一：**加解密与源 IP 校验**。它完全不关心数据包的目的 IP 是给本机的、还是需要转发给公网的——目的 IP 的路由决策、防火墙过滤以及 NAT 转换，**100% 由操作系统内核的网络协议栈接管**。

---

## 二、 完整接收与转发流程（Inbound & Forwarding Lifecycle）

假设场景：
* **客户端虚拟 IP**：`10.0.0.2`（配置在服务端的 `AllowedIPs = 10.0.0.2/32` 中）
* **服务端虚拟 IP**：`192.168.1.1`（TUN 设备 IP）
* **目标地址**：客户端试图访问公网 IP `8.8.8.8`

整体流量走向图：

```text
[公网传输的 UDP 密文包]
        │
        ▼
[1. 物理网卡 eth0 (UDP :51820)]
        │
        ▼
[2. wireguard-go 用户态进程]
        │  ├─ 2.1 提取外层 UDP 报文并进行 ChaCha20-Poly1305 解密
        │  ├─ 2.2 校验解密包的源 IP (10.0.0.2) 是否属于该 Peer 的 AllowedIPs
        │  └─ 2.3 调用 write(tun_fd, packet) 将明文包写入 TUN 设备
        ▼
[3. TUN 虚拟设备 (utunX / wg0)]
        │
        ▼
[4. 操作系统内核网络协议栈 (L3 路由 & iptables/nftables)]
        │  ├─ 4.1 检查目的 IP (8.8.8.8)：发现不是本机 TUN 的 IP
        │  ├─ 4.2 检查 IP Forwarding：确认 net.ipv4.ip_forward == 1
        │  ├─ 4.3 路由查找 (Routing Lookup)：确认 8.8.8.8 的出口为物理网卡 eth0
        │  └─ 4.4 执行 iptables MASQUERADE (源 IP 从 10.0.0.2 改为 服务端公网 IP)
        ▼
[5. 物理网卡 eth0] ───> 发往公网 8.8.8.8
```

## 三、 各阶段详细步骤拆解

### 阶段 1：UDP 密文接收与用户态处理 (`wireguard-go`)

1. **物理 Socket 监听**：
   `wireguard-go` 监听在物理网卡绑定的 UDP 端口（如 `51820`），接收外层数据包。
2. **解密与安全校验（Cryptokey Filtering）**：
   * 使用与该 Peer 协商好的对称密钥解密出**原始明文 IP 包**（源 IP: `10.0.0.2`，目的 IP: `8.8.8.8`）。
   * **安全校验（反 IP 欺骗）**：`wireguard-go` 校验解密出来的源 IP `10.0.0.2` 是否存在于该 Peer 的 `AllowedIPs` 配置中。
     * 若**在**白名单中：校验通过，继续处理。
     * 若**不在**白名单中：直接静默丢弃（Drop），不进行后续任何操作。
3. **写入 TUN 设备（关键点）**：
   * 校验通过后，`wireguard-go` 调用系统调用 `write(tun_fd, buf, len)`，将明文 IP 包**无脑写入** TUN 设备的字符文件描述符。
   * **注意**：此时 `wireguard-go` 的处理逻辑完全结束，它不会去判断 `8.8.8.8` 是否属于 TUN 网卡网段。

---

### 阶段 2：内核网络协议栈路由与 NAT 转发

数据包被写入 `tun_fd` 后，在操作系统内核视角下，这等同于 **“网卡 `wg0` / `utun` 接收到了一个正常的入站 IP 数据包”**。

1. **L3 入站检查与目的地址判断**：
   内核协议栈提取 IP 报头，检查目的地址 `8.8.8.8`：
   * 内核发现 `8.8.8.8` 既不是 `192.168.1.1`，也不是本机的任何其他网卡 IP。
2. **IP 转发判断（IP Forwarding）**：
   * 内核检查系统参数 `net.ipv4.ip_forward`：
     * 若未开启（`0`）：内核直接丢弃该数据包。
     * 若已开启（`1`）：内核将该包标记为“需要转发的数据包”，送入转发流程（`FORWARD` 链）。
3. **路由查找（Routing Lookup）**：
   内核查阅系统主路由表，寻找匹配 `8.8.8.8` 的最佳下一跳。匹配到默认网关，确定出口网卡为物理网卡 **`eth0`**。
4. **iptables / nftables 防火墙与 NAT 处理**：
   数据包流经 Linux 内核网络过滤框架：
   * **`FORWARD` 链**：评估防火墙规则，允许流量通行。
   * **`POSTROUTING` 链（SNAT / MASQUERADE）**：
     * 触发 `iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE` 规则。
     * 内核修改数据包的 IP 报头：将**源 IP 从 `10.0.0.2` 替换为服务端物理网卡的公网 IP**（如 `203.0.113.1`），并记录连接追踪表（Conntrack）。
5. **物理网卡发出**：
   修改后的数据包被送往 `eth0` 网卡驱动，正式通过物理链路发往公网 `8.8.8.8`。

---

## 四、 总结

1. **WireGuard 不做高级路由决策**：`wireguard-go` 作为一个 L3 隧道程序，它的生命周期在把解密包 `write()` 进 TUN 设备时就已结束。
2. **跨网段流量依赖内核**：服务端能否把异网段流量发往公网，完全取决于**操作系统内核是否开启了 IP 转发（`ip_forward=1`）** 以及 **是否配置了正确的 NAT/MASQUERADE 规则**。
3. **唯一会丢包的原因**：在写入 TUN 之前，WireGuard 过滤数据包的**唯一依据是源 IP（Source IP）是否符合 `AllowedIPs`**，而不是目的 IP。
